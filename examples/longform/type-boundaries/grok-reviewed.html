compile time 与 runtime 观察不同的东西

从 TypeScript 注解到不可信 JSON：一次请求的边界

IDE 里的绿色提示、HTTP 2xx 和 response.json() 成功，常常被看成同一件事：数据已经是 User。题目提供的 loadUser 把这几件事叠在一个函数里，但它们证明的证据并不相同。

类型注解和 as User 改变的是静态检查器对源代码的理解，在通常的 TypeScript 转译中会被擦除；它们不是运行时防护墙。一次请求要分别跨过地址编码、网络 Response、HTTP 状态、JSON 语法，以及（若另加解析器）值结构。每一步成功只新增一种证据，还缺另一种证据。不能把所有绿色状态都叫作“验证成功”。

/api/users/ 只是示例中的相对路径。用户资料、日志和域名均为虚构；讨论不需要访问任何接口。本页只用题目提供的材料作事实来源，没有插画，也没有调用外部接口。

先分开两条线，再看同一次请求

目标读者能读简单代码，但容易把 IDE 中的绿色提示、HTTP 成功和数据可信混在一起。compile time 指工具检查源代码的阶段，runtime 指编译后的 JavaScript 实际执行时。二者协作，却观察不同的东西。

compile time
静态工具根据类型注解、声明的假设和 as User 这类 type assertion，判断源代码是否满足当前规则。它看不见这次请求真正返回的 JSON。
runtime
已经转译后的 JavaScript 按语句执行：编码地址、发起 fetch、看 response.ok、解析正文。异常会让 async 函数返回的 Promise 拒绝。
type assertion
as User 影响静态检查器对表达式的理解。它不会在响应解析之后再执行第四个“断言成功”步骤，不会调用验证器，也不会增加或改写 JSON 字段。

把注解画进执行箭头里，会看起来像“类型检查也是一次运行时关卡”。本页把静态说明放在旁边，把真正可能抛错或兑现的步骤放在执行路径上。

一次请求里，每条边界新增的证据
边界 成功说明了什么 尚未说明什么
TypeScript 检查通过 代码满足当前静态规则和已声明假设 外部 JSON 在运行时真实长相
地址编码完成 这个字符串已按 URI component 规则编码 身份、权限、用户一定存在

response.ok 为真 HTTP 状态是 200–299 正文是合法 JSON 或字段正确
response.json() 兑现 正文被解析为合法 JSON 值 它一定是具备两个字符串字段的对象

原函数是分析对象，不是已经加过校验的成品

下面这段是题目提供的原函数。它不包含输入格式修正或 JSON schema 校验。缩进与换行只是为了阅读。

type User = {
  id: string;
  name: string
};

async function loadUser(id: string): Promise<User> {
  const response = await fetch(`/api/users/${encodeURIComponent(id)}`);
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return (await response.json()) as User;
}

类型承诺来自哪里

id: string 告诉 TypeScript 调用者应传入字符串。Promise<User> 告诉 TypeScript：正常完成的 Promise 被当作提供 User。这不是运行时的防护墙。普通 JavaScript 调用者、被绕过的检查或断言都可能带来不同值。

本材料随后分析的是字符串输入的正常前提。不要因此把原函数改称具备完整输入验证。

断言在什么位置、做什么

最后一行的 as User 是 TypeScript 的 type assertion。它只改静态检查器对这个表达式的理解。在通常的 TypeScript 转译中，它被擦除。

  • 它不会在 response.json() 之后再执行第四个“断言成功”步骤。
  • 它不会调用验证器。
  • 它不会增加或改写 JSON 字段。

type User 和函数的类型注解同样不会变成相应的运行时对象检查。

Promise 有两条结局

async 函数总返回 Promise。函数体中的异常会使它拒绝。Promise<User> 只描述正常兑现值的静态类型，不表示请求、解析或业务逻辑必然成功。

await 等待一个 Promise 的结果，并可能重新抛出拒绝原因。它不会替调用者捕获异常。调用者仍需决定怎么显示失败、记录问题或重试。

读到这里可以先记住的限度：给原函数配一句“收到合法用户数据才返回”，会把原本不存在的验证写进去。原函数在 JSON 解析成功后，把得到的值当作 User 交出去；值是否真有两个字符串字段，要到运行时用到字段、或另加解析器时才会暴露。

按运行时实际发生的事划分边界

下面按原函数语句的顺序走。每一步都可能成功并继续，也可能在这里离开。离开之后，后面的检查根本不会发生。

主路径上，传入普通字符串且编码成功，才会继续调用 fetch。编码表达式自己的失败发生在请求发出之前，所以排错时不能默认“先有服务器响应，再有前端错误”。

可选解析器是另一段代码，不冒充原行为

如果产品要在入口处拒绝不符合结构的 JSON，可以另加下面的解析器，并把原函数最后一行替换为：

return parseUser(await response.json());

这是建议的改动版本，不是 as User 原本偷偷完成的工作。类型收窄让 TypeScript 能理解通过检查后的字段，真正执行检查的仍是普通 JavaScript 条件。

function parseUser(value: unknown): User {
  if (typeof value !== "object" || value === null || Array.isArray(value)) {
    throw new Error("Expected a user object");
  }

  if (
    !("id" in value) ||
    !("name" in value) ||
    typeof value.id !== "string" ||
    typeof value.name !== "string"
  ) {
    throw new Error("Expected string id and name");
  }

  return { id: value.id, name: value.name };
}

检查对象时为什么要写这么多条件

JavaScript 的 typeof null 是 "object"，数组的 typeof 也为 "object"，所以上面的非空及 Array.isArray 检查都有独立意义。两个字段必须存在且实际值都是字符串。数值 17 即使可以转成文本，也会被这个解析器拒绝，因为它没有进行隐式或显式强制转换。

原函数最后一行

return (await response.json()) as User;

解析成功就兑现该值。200 的 null、错误类型字段都会过去。

改变的是静态理解，不是值。

建议的替换

return parseUser(await response.json());

结构不符就抛错。通过后返回只有 id 和 name 的新对象。

改变的是遇到具体值时做什么。

故意有限的契约

允许的
空字符串；输入里包含额外字段。解析器返回一个只有 id 和 name 的新对象，不保留那些额外字段。
没有检查的
ID 格式、显示名长度、姓名真实性、数据是否过期、当前用户权限或服务端签名。
通过之后
仍可能需要业务验证。不能称为“所有数据已经安全可信”。给这段解析器配一句“解决了一切网络错误”，会超出它只检查值结构的职责。

它预期的输入是 JSON 解析结果

这里解析器的预期输入是 response.json() 的结果，即从 JSON 文本产生的值。若把它作为接受任意 JavaScript 对象的通用安全库，in 会考虑继承属性，属性访问也可能触发 getter，因而需要另行定义更严格的契约。

本文不提供这种通用库保证，也没有使用这个局限来否认它对给定 JSON 场景的结构检查价值。

同一状态码，正文不同，结局也可以不同

以下是虚构离线记录，不是已访问接口的日志。body 是服务端发送的正文文本；网络失败那行没有响应。若显示同一个状态码两次，它们也可能因为正文不同走向不同结果。

case alpha: status=200; body={"id":"u-17","name":"林 Ada"}
case beta:  status=404; body={"id":"u-17","name":"林 Ada"}
case gamma: status=200; body=<html><body>Sign in required</body></html>
case delta: status=204; body=<empty bytes, not the literal text shown here>
case epsilon: status=200; body=null
case zeta: status=200; body={"id":17,"name":false}
case eta: network disconnect before any Response exists
case theta: status=200; body={"id":"","name":"","role":"maintainer"}
这些区别来自给定代码，不依赖真实服务器是否上线
记录 到达哪条边界 原函数 若使用可选 parseUser
alpha 200，正文是两个字符串字段的对象 兑现两个字符串字段的对象 同样能返回这两个字段
beta 404；正文碰巧也是合法 JSON 抛出 HTTP 404，且不解析正文 走不到解析器
gamma 200，正文是 HTML 在 JSON 解析时拒绝 走不到结构检查
delta 204，空正文 在 JSON 解析时拒绝 走不到结构检查
epsilon 200，正文为 null 兑现 null 拒绝：不是用户对象
zeta 200，id 是 17，name 是 false 兑现这份对象；as User 不改类型 拒绝：两个字段都不是 string
eta 在拿到 Response 之前断开 拒绝，还没有 response.ok 走不到解析器
theta 200，两个字段是空字符串，另有 role 合法 JSON 对象会被兑现；as User 不删除 role 通过；返回的新对象不含 role

beta 与 alpha 的正文可以相同，却在 response.ok 分开。gamma、delta 的 HTTP 都成功，但 JSON 解析失败；epsilon、zeta 解析成功，原函数会兑现，可选解析器才拒绝它们的形状。theta 在两版中都能兑现，解析器只是返回不含额外字段的新对象。窄屏可横向滚动表格。

把“HTTP 成功”和“得到 User”绑在一起，解释不了 beta 以外的多数行。把“JSON 解析成功”和“字段正确”绑在一起，解释不了 epsilon 与 zeta。

alpha / beta：正文可以一样，HTTP 边界先说话

alpha 状态 200，原函数兑现 id 为 "u-17"、name 为 "林 Ada" 的对象。beta 的正文可以完全相同，但状态是 404，原函数抛出 HTTP 404，并且不解析正文。错误响应体即使是格式正确的 JSON，也不会在这次运行里进入 response.json()。

gamma / delta：2xx 仍可能在 JSON 语法处拒绝

gamma 是 200，正文却是 <html><body>Sign in required</body></html>。delta 是 204，正文是空字节，不是字面上的那段说明文字。二者都可能在 response.json() 拒绝。Content-Type 写了 JSON，并不能代替实际按 JSON 语法解析。

epsilon / zeta：原函数会兑现，可选解析器会拒绝

epsilon 的 200 正文是 null，原函数兑现 null。zeta 兑现 {"id":17,"name":false}。as User 不会把 17 变成字符串，也不会把 false 变成人名。可选解析器对 null、数组和非对象走第一条错误；对存在但不是字符串的字段走第二条错误。

eta / theta：Response 之前的网络失败，与结构通过但契约有限

eta 在任何 Response 存在之前就因网络断开拒绝，不能把它显示成 HTTP 错误或类型断言失败。theta 的两个字段类型正确，即使都是空字符串，也会通过可选解析器；返回的新对象不含 role。原函数的 as User 不会改写 JSON 字段，因此解析得到的对象仍可带着 role 被交出去。空字符串通过，只说明最小结构检查允许它，不说明这是合法业务用户。

标识要精确，错误提示也要对上抛出位置

长标识不一定敏感，也不代表合法授权。例如下面这个字符串可以作为示例：

user_import_2026_autumn_public_workshop_team_north_building_room_204_record_000000000017

下面这一整段是使用保留无效域名的阅读样例，不是调用地址，不应拿它代替原函数的相对 URL /api/users/${encodeURIComponent(id)}：

https://example.invalid/api/users/user_import_2026_autumn_public_workshop_team_north_building_room_204_record_000000000017?include=profile%2Cpreferences%2Cmembership&requestPurpose=offline_type_boundary_explanation

原代码和新方案需要分别归因

不要加给原函数
“收到合法用户数据才返回”。这会把原本不存在的验证写进去。
不要加给解析器
“解决了一切网络错误”。它只检查值结构，不负责 fetch 拒绝、HTTP 非 2xx 或 JSON 语法失败。
错误提示应分开
说清楚是请求未完成、HTTP 不成功、JSON 不可解析，还是结构不符。不能把它们全部显示成“类型断言失败”。

错误在哪个范围被捕获

若调用者把 await loadUser(id) 和后面的 user.name.toUpperCase() 放在同一个 try 内，catch 既可能接到加载过程的拒绝，也可能接到加载兑现后访问字段产生的异常。捕获到错误不自动证明问题来自网络。

若只对 loadUser(id) 返回的 Promise 附加拒绝处理，后续独立语句的异常也不会因此被那个处理函数捕获。错误的类别需要结合实际抛出位置判断，不能仅按最终提示文字反推。

同一段 try 里可能出现的两类失败：

加载过程拒绝：编码 URIError、fetch 在无 Response 时拒绝、非 2xx 的 HTTP ${response.status}、JSON 解析拒绝，或可选 parseUser 的结构错误。

加载兑现之后：例如对 null 或 false 调用 toUpperCase()。这时请求路径已经走完，失败发生在使用字段的语句。

改类型声明，不会凭空改掉服务端正文

只把某个表达式的静态类型改成更宽或更窄的声明，不会凭空改变服务端正文。相反，增加 parseUser 的实际条件分支，会让原本能兑现的错误结构在运行时拒绝。

静态修改

改注解、改 as、让编辑器不再报错。

改变的是工具接受哪些写法。

epsilon 的 null 仍会被原函数兑现。

行为修改

增加普通 JavaScript 条件，例如 parseUser。

改变的是程序遇到某个具体值时做什么。

同样的 null 会在运行时被拒绝。

这也解释了为什么修复编辑器报错与修复外部数据问题可以有关联，却不一定是同一次修复。

  1. 先问这一步新增了哪种证据。TypeScript 通过、地址编码完成、fetch 兑现、ok 为真、JSON 解析成功、结构检查返回，六行不要互相顶替。
  2. 再问还缺哪种证据。缺的往往是正文形状、字段类型、授权或业务规则，而不是再加一个更绿的类型。
  3. 给失败命名时对准抛出点。请求未发出、没有 Response、HTTP 非 2xx、JSON 不可解析、结构不符、使用字段时崩溃，不是同一种“断言失败”。
  4. 需要入口处拒掉坏 JSON 时，写运行时条件。把最后一行换成 parseUser(...) 是另一段代码；写清它仍然不检查权限、长度和非空。

假设、来源，以及比喻不能写成排他清单

本页事实来自题目提供的材料：原函数、parseUser、边界表和八条虚构记录。没有访问 /api/users/，也没有把阅读样例域名当作可调用地址。

JavaScript 可以在页面加载时创建内容，可以按定时器更新内容，也可以处理用户互动，并非只在点击之后执行。HTML 的原生 details 元素本身能够展开收起，不要求 JavaScript。它们与 TypeScript 静态类型的关系是互补职责。不能将简化的角色比喻写成排他的能力清单，例如把“静态类型负责形状”说成 JavaScript 运行时不能做结构检查，或把“页面交互”说成只能发生在点击之后。

  • 可以支持的结论：在给定函数与可选解析器下，每一步成功证明什么、不证明什么；八条记录如何因状态、语法和形状相互独立而分叉。
  • 不能支持的结论：真实接口的行为、浏览器或运行时的全部异常分类、把 parseUser 当成任意对象的通用安全库、或“通过最小结构检查后数据已经安全可信”。
  • 教学假设：讨论默认走字符串输入且编码成功的主路径，同时保留 URIError 这一反例；不把原函数改写成已有完整输入验证。
  • 未核验：本页未在浏览器中做独立验收；插画预算为零，没有生成或引用图片。
