编译通过了，数据就可信了吗？

还不能这样判断。沿着一段 loadUser 代码，把静态类型、地址编码、网络、HTTP、JSON 和值的结构逐层拆开：每跨过一步，究竟多知道了什么？

as User 让 TypeScript 把一个值当作 User，却不会在 runtime 检查这个值。HTTP 2xx 也只说明状态成功。只有实际执行字段检查的代码，才能为字段结构提供证据；即使结构通过，也还没有证明身份、权限和全部业务规则。

01 / THE ORIGINAL CONTRACT

先把原函数，按它真正做的事读一遍

这段代码是分析对象。它编码地址、发请求、检查 HTTP、解析正文，并把解析结果的静态类型断言为 User。它没有输入格式修正，也没有 JSON schema 校验。

type User
定义检查器所理解的结构：id、name 都应是字符串。它不会自动生成检查响应对象的 JavaScript。
id: string
要求遵守 TypeScript 检查的调用者传字符串。普通 JavaScript 调用者、被绕过的检查或断言，仍可能带来不同值。后文的正常路径以字符串输入为前提。
Promise<User>
描述正常兑现值的静态类型，并不保证 Promise 一定兑现。async 函数总返回 Promise；函数体中的异常会让它拒绝。
as User
这是 type assertion。它改变静态理解，不调用验证器、不增添字段、不修正字段类型。通常转译后，断言本身不再存在。

编辑器里像 User，运行时可以是 null

设响应是 HTTP 200，正文恰好是 null。HTTP 检查通过，JSON 解析也成功。原函数随后兑现的实际值就是 null，不会因为返回类型写成 Promise<User> 而变成对象。

静态承诺依赖声明与假设。这里的断言告诉检查器接受结果；它没有提供“刚刚查看过外部字段”的运行时证据。调用处能写下 user.name，与这个字段实际可用，是两件需要分别判断的事。

02 / EXECUTION & EXITS

运行路径上，哪里继续，哪里退出？

按 JavaScript 实际发生的顺序走。每一步的“继续”只允许进入下一步；它没有替下一步完成检查。某一步失败时，后续步骤不会在本次原函数调用中继续执行。

这也给排障规定了顺序：如果编码就失败，服务器并未收到这次请求；如果原函数抛出了 HTTP 404，就不该声称本次已经检查过正文；如果拿到了一个对象，也仍需知道它是否经过结构检查。

03 / WHAT SUCCESS PROVES

每个“成功”，都有自己的证据范围

把“成功”改说成一句可核对的话：哪项操作，确认了哪项性质？下表中的右栏是当前证据留下的空白，不能用上一步的绿色状态填补。

从静态检查到结构检查：新增证据与剩余边界
边界通过新增证据尚不能推出
TypeScript 检查通过源代码符合当前静态规则及已声明的假设。外部 JSON 在 runtime 真的长这样。
地址编码完成字符串已按 URI component 规则编码。用户存在，调用者有身份或查看权限。
fetch 兑现拿到一个 Response。HTTP 是 2xx，正文可解析，字段符合 User。
response.ok 为真状态码位于 200–299。正文是 JSON，更不能推出字段正确。
response.json() 兑现正文被解析为合法 JSON 对应的值。结果是非空对象，且有两个字符串字段。
可选 parseUser 返回在给定 JSON 输入场景中，两个指定字段通过最小结构检查。字符串非空、长度合规、身份真实、授权有效或业务规则全部成立。

窄屏可横向滚动表格；键盘聚焦表格区域后可使用左右方向键。最后一行属于新增方案，原函数不会执行它。

HTTP 与 JSON 语法分开看

同样是 HTTP 200，正文 {"id":"u-17","name":"林 Ada"} 可被解析，HTML 登录页则不可被当成 JSON 解析。HTTP 成功没有决定正文语法。

JSON 语法与 User 结构分开看

null 与 {"id":17,"name":false} 都是合法 JSON，却不满足这份 User 的字段结构。JSON 解析没有决定对象是否适用。

授权另有职责。encodeURIComponent 不做身份认证或权限判定，也不清除响应 JSON 中的恶意内容。服务端及相应应用逻辑仍须负责授权；字段类型正确也不能代替这些判断。

05 / OPTIONAL RUNTIME PARSING

如果要拦住错误结构，就加上实际检查

parseUser 接收 unknown，通过条件判断再返回 User。这里的 type narrowing 让 TypeScript 理解检查后的字段；真正执行检查的，仍然是那些普通 JavaScript 条件。

这是可选的新方案。它会改变原函数遇到错误结构时的 runtime 行为，不能把它归因给原来的 as User。它也没有给请求参数 id 增加完整的运行时输入验证。

求值顺序很重要：先等待 response.json()。如果解析拒绝，parseUser 就不会执行；如果解析成功，解析出的值才成为它的输入。如果它随后抛错，外层 async 函数的 Promise 会拒绝。

06 / THE LIMIT OF THIS CONTRACT

通过最小结构检查，仍只跨过这一道边界

为什么要单独排除 null 和数组？

JavaScript 中 typeof null 为 "object"，数组的 typeof 也为 "object"。所以只判断 typeof 不够：非空判断和 Array.isArray 在这份契约里各有作用。

第一层通过后，还没有证据说字段齐全。第二层才确认 id 和 name 存在，且每个实际值都是字符串。17 即使可以转成 "17"，也会被当前解析器拒绝。

theta 显示了两个容易漏读的选择

空字符串允许通过，额外字段允许存在于输入中。解析器检查的是两个字段的类型，而不是非空规则；它通过重建对象丢弃额外字段，并没有把“多了一个字段”本身作为错误。

这份代码明确做了什么

  • 排除非对象、null、数组。
  • 检查两个指定字段存在且为字符串。
  • 返回只含 id、name 的新对象。

仍需另定规则的事情

  • ID 格式、非空、显示名长度。
  • 姓名真实性、数据是否过期。
  • 当前用户权限、服务端签名及其他业务规则。

为什么不把它宣传成任意对象的通用安全库？

这里的预期输入是 response.json() 从 JSON 文本产生的值。如果扩展到任意 JavaScript 对象，in 会考虑继承属性，读取属性也可能触发 getter。届时需要重新定义更严格的契约。

适用范围是给定 JSON 场景下的最小结构检查。任意对象场景的局限不否定它在这里的价值，但也不能被省略后推广为“所有数据已经安全可信”。

追问：检查字段存在，是否等于“字段是自身属性”？

不等于。这里使用的是 "id" in value，没有声明“只接受自身属性”的条件。对任意 JavaScript 对象，继承链上的属性也能影响结果。材料没有给出通用安全库的替代实现，因此本文也不补造这种保证。

07 / PROMISE & CATCH SCOPE

错误被捕获了，不等于错误来自网络

await 等待 Promise 的结果；Promise 拒绝时，它可能重新抛出拒绝原因。它不会替调用者捕获异常。调用者仍要决定怎样展示失败、记录问题或重试。

接着要看捕获范围。loadUser 的加载过程与调用者使用结果，是两个可能出错的位置。把它们放在同一个 try 中，两个位置的异常都可能到同一个 catch。

只给加载 Promise 加拒绝处理，覆盖范围不同

在示例 B 中，.catch 也没有把原来的 loading 改成成功。如果加载拒绝，await loading 仍会让 showUserLater 拒绝；如果加载兑现但后续字段使用抛错，外层 showUserLater 的 Promise 也会拒绝，需要它的调用者处理。

错误展示应对应失败阶段，而不是统一归为“类型断言失败”
实际位置本例可以辨认的类别不能单凭它断言
地址构造编码失败，例如 URIError。服务器已收到请求。
fetch请求未取得 Response。一定有一个 HTTP 失败状态码。
!response.okHTTP 不成功，原函数附带状态码。错误正文已被解析。
response.json()正文读取或 JSON 解析失败。已经拿到可供字段检查的值。
可选 parseUser对象或字段类型不符合最小结构。所有业务规则都不满足。
调用者使用字段加载之后的使用异常。一定是网络出错或加载 Promise 拒绝。

表格可横向滚动。这些是解释类别，并非新增的生产错误分类器。判断类别需要结合实际抛出位置，不能只凭最终提示文字反推。

09 / TAKE THE DISTINCTION WITH YOU

下次读代码，先找真正执行的条件

修复编辑器报错与修复外部数据问题可能有关，但不一定是同一次修复。判断一项修改的作用，先问它增加的是静态说明，还是 runtime 确实执行的操作。

只改变静态类型

把表达式的类型声明得更宽或更窄，会改变检查器接受哪些写法。没有新增运行时逻辑时，它不会凭空改变服务端正文，也不会替 JSON 增添字段。

同一份 zeta：只改变对它的类型理解，实际的 17、false 仍留在原值里。

增加 parseUser 条件

JSON 解析后真正读取并判断字段。原先能兑现的错误结构，现在会在实际分支中抛错，导致加载 Promise 拒绝。

同一份 zeta：第二层字段检查拒绝它。这是行为修改，有具体输入和出口可指认。

角色分工，也别写成排他的能力清单

compile time 是工具检查源代码的阶段，runtime 是编译后的 JavaScript 实际执行时。JavaScript 可以在页面加载时创建内容、按定时器更新，也能响应交互；它并非只在点击后执行。

HTML 的原生 details 本身就能展开收起，不要求 JavaScript。本页的补充推导使用这种元素。把 HTML、JavaScript 与 TypeScript 的互补职责看清楚，比给每种语言划一张绝对能力清单更准确。

用四个问题复查自己的解释

  1. 承诺从哪里来？来自类型声明、断言，还是一次已经执行的条件检查？
  2. 值走到哪一步？编码、请求、HTTP、JSON、结构检查和后续使用，不要跳着归因。
  3. 成功还剩什么未知？把非空、格式、真实性、权限等尚未检查的规则写出来。
  4. 谁捕获哪一段？沿着 Promise 与 try 的实际范围定位，别用统一错误提示反推原因。

停一下，用反例确认理解

HTTP 404 的正文恰好符合 User，原函数会返回它吗？

不会。原函数先检查 response.ok，在 404 处抛出 HTTP 404，本次调用不再执行 JSON 解析。正文看起来正确不能绕过前面的失败出口。对应案例 beta。

204 空正文与 200 的 null，为什么结局不同？

两者的 HTTP 检查都通过。但空正文没有可解析的 JSON 文本，所以 delta 在解析时拒绝；正文文本 null 是合法 JSON，所以 epsilon 被原函数兑现为 null。加上 parseUser 后，epsilon 才在结构检查处拒绝。

parseUser 接受 theta，是否意味着空 ID 合法、角色已验证？

不能这么推。当前契约只确认两个字段是字符串，因此空字符串可以通过；输入中的 role 被丢弃，并未变成一次授权判断。业务是否合法仍要有对应规则。见结构检查边界。

同一个 catch 打印错误，是否足够证明 fetch 拒绝？

不够。如果加载和字段使用都位于同一个 try，加载已兑现之后的字段异常也可能进入那个 catch。需要结合抛出位置判断。见捕获范围图。
