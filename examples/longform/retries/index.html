AhaFold / The Lantern guide

A booking is a fact. A response is evidence.

Networks, explained through two theatre seats

Did my seats
get booked?

You ask for seats C07 and C08. The screen waits, then times out. The ticket desk may already have reserved them. How can you try again without accidentally making a second booking?

A missing response leaves the outcome unknown. Preserve the original booking identity, retry only within its attempt and time limits, and check the authoritative record when the evidence is incomplete.

Lantern is a fictional community performance booking system. Its supplied rules allocate seats; they collect no money and contact no real service. All people, identifiers, dates, and events here are teaching examples. These status meanings are Lantern’s contract, not universal rules for other APIs.

The whole journey

Keep the intention steady as the evidence changes

The client is the app making the request. The server is the ticket desk’s system, which commits the reservation. A network message connects them, but that message can disappear after the server has done its work.

  1. Preserve what the person meant.Save the intention, exact request bytes, key, and creation time before sending.
  2. Separate the record from the reply.A reservation may exist even when its response never arrives.
  3. Choose an action from the evidence.Confirmed, pending, rejected, and unknown outcomes lead to different next steps.
  4. Retry within both limits.At most four total attempts, with the same key and body, before the client’s conservative 24-hour cutoff.
  5. Check later deliveries.Authenticate callbacks, recognize repeats, and use revisions to protect newer state.
  6. Resolve what remains uncertain.Read authoritative status using the original records; involve a person if that still cannot settle it.

This is a map of responsibilities, not a promise that every booking follows every step. A valid final response stops dispatching; a pending response goes to reconciliation; an identity conflict stops for investigation.

01 / Identity

One decision can travel more than once

Source rules R01–R03

Mina Patel wants C07 and C08 for the Lantern autumn matinee. Her booking intention is that one decision. An HTTP attempt is one network request carrying it. A durable reservation is the committed server record that actually consumes the seats.

Write the intention down before sending it

The client’s durable local ledger is a record that survives a restart. In this teaching contract, the client saves four things before the first dispatch:

Intention ID
A stable label for the person’s decision.
Exact body
The original UTF-8 bytes, including the performance, seat choices, and attendee name. UTF-8 is the text encoding; the comparison is of the encoded bytes.
Idempotency key
The server’s label for recognizing repeat attempts for that body. “Idempotent” here means repeat accepted requests can refer to the same effect instead of creating another reservation.
Creation time
When the client created the key, used to calculate its conservative retry cutoff.

If saving fails, do not dispatch. After a restart, read and check the existing record before resuming. A restart must not invent a new key for an intention whose outcome is still uncertain. The attempt count also persists, as the retry policy explains.

In the supplied example, the performance is lantern-autumn-matinee-2026-10-17, the seats are C07 and C08, the attendee is Mina Patel, and the local key creation time is 2026-10-01T10:00:00Z. The complete ledger record preserves the long identifiers and exact request text.

“Same meaning” is weaker than “same bytes”

Every retry must reuse both the original key and the exact original body bytes. Lantern does not decide that two differently written JSON objects are close enough.

Original fragment

{"seatIds":["C07","C08"],"attendeeName":"Mina Patel"}

Reordered fragment

{"attendeeName":"Mina Patel","seatIds":["C07","C08"]}

These are abbreviated teaching fragments, not the complete request. They describe the same fields, but their byte sequences differ. Lantern’s key binding cares about that difference.

Changed seats, changed name, or changed JSON property order require an explicit new intention. Reconcile any unresolved earlier intention first. Reusing its key with different bytes returns 409 KEY_PAYLOAD_MISMATCH; that conflicting attempt creates no new reservation, and the client stops to investigate.

Think of the key as a claim ticket attached to one exact request. The analogy ends at the contract boundary: a ticket alone does not promise seats, and the server’s memory of it is limited to 24 hours from first acceptance.

02 / Uncertainty

The server can finish before the client knows

Source rules R05–R06

A response is a message about the server’s work. Delivering that message is a separate event from committing the work. The gap between those events is where uncertainty appears.

A timeout or disconnect does not prove the booking failed, that the seats remain free, or that a fresh booking is safe. The app keeps the original identity and records UNKNOWN. A retry is permitted only if the response, budget, and time rules allow it.

A replay can be successful without doing new work

A valid final 201 RESERVED supplies a reservation identifier and the server’s current reservation revision. It confirms a durable reservation for this intention. If the client repeats a completed key, it may receive 200 RESERVED with the same reservation identifier. That attempt allocated no additional seats.

A later reservation.created callback is another channel carrying a committed fact. If the client gets both the response and that callback, it must connect them to the same local booking.

202 PENDING means “processing acknowledged.” It does not prove a reservation has committed. The next action is to reconcile status, not immediately send another booking request.

03 / Evidence

Source rules R06–R09, R13–R14

“This attempt made no reservation” is a scoped claim. A 429 after an earlier timeout does not tell you what that earlier attempt did. Likewise, a conflicting request’s rejection does not erase a reservation made for the original body.

A response or callback naming a different intention must not silently replace the original record. Callback signatures and bindings have an additional authentication gate.

Check your reasoning: a “success” response has no reservation identifier. Are the seats confirmed?

No. Required evidence is missing. Keep the intention unresolved and reconcile or escalate; the status label alone does not establish which durable reservation belongs to this intention.

04 / Attempts and seconds

Four attempts total. Three waits between them.

Source rules R08–R10

The automatic budget is one original attempt plus at most three retries. Count each dispatch durably before sending. Restarting the application does not reset that count. Waiting itself does not consume an attempt.

Fix the teaching assumptions before calculating.

  • Every attempt takes exactly 0.5 seconds to reach its response or timeout.
  • The base waits before attempts 2, 3, and 4 are 1, 2, and 4 seconds.
  • Each wait begins after the previous attempt finishes or times out.
  • Clocks are stable and there is no jitter, meaning no random adjustment to the delays.
  • For the baseline below, the first three attempts time out, the fourth succeeds, and enough time remains before expiry.

Build the time line from the previous finish

Next start = previous finish + required wait

Finish = start + 0.5 seconds

Rate limiting can lengthen a wait

After a retryable 429, compare the next base wait with that response’s valid integer Retry-After, measured in seconds. max means “take the larger value.”

Required wait after 429 = max(next base wait, Retry-After)

After attempt 2: max(2 s, 6 s)6 seconds
With a zero delay: max(2 s, 0 s)2 seconds
With an equal delay: max(2 s, 2 s)2 seconds

Do not add the two waits. A base wait of 2 seconds and Retry-After: 6 requires 6 seconds, not 8. A zero delay never removes the base wait.

Baseline: attempt 2 times out

It finishes at t = 2 s. Wait 2 s.

Attempt 3 starts at t = 4 s.

It finishes at 4.5 s; after another timeout, attempt 4 starts at 8.5 s and ends at 9 s.

Variant: attempt 2 returns 429 with 6 s

It still finishes at t = 2 s. Wait 6 s.

Attempt 3 starts at t = 8 s.

If attempt 3 then times out at 8.5 s, attempt 4 starts at 12.5 s and ends at 13 s.

The variant changes only the second observation and its required delay. It uses the same 0.5-second attempt duration, sufficient remaining key time, and a successful fourth attempt. These additional times are derived from the supplied rules, not observed network measurements.

A calculated next start is still conditional. Stop if the budget is exhausted or the required wait reaches or passes the conservative expiry time. A pending asynchronous operation goes to reconciliation instead of an immediate new booking dispatch.

Real systems must account for variable latency, clock uncertainty, cancellation, and often jitter. Those considerations can change a real schedule. They are not hidden extra terms in this fixed teaching example.

Check your reasoning: the app restarts after attempt 3. How many automatic attempts remain?

At most one: attempt 4. The persisted count still includes the first three dispatches. That last attempt is allowed only if the observation is retryable and the time limit still permits it. A restart supplies neither a new budget nor a new identity.

05 / The retention boundary

The server and client start their 24-hour clocks at different moments

Source rules R04, R09, R15

The server keeps the key’s binding and final outcome for 24 hours from the first accepted request. Concurrent requests with that same key are serialized: they are handled in an order that allows at most one reservation to commit. Later accepted attempts receive the stored outcome; an operation still processing may return 202 PENDING.

The client uses an earlier, conservative boundary: 24 hours after local key creation. It stops automatic retries then, even if the server first accepted the request later.

Calculate the stop boundary from the supplied record

The key was created at 2026-10-01T10:00:00Z. Its conservative client cutoff is therefore 2026-10-02T10:00:00Z. The Z marks UTC. The material does not give the server’s first acceptance timestamp, so there is no basis for replacing this with a later cutoff.

Expiry = local key creation time + 24 hours

Required next start = previous finish + required wait

If required next start ≥ expiry: stop automatic dispatch and reconcile. Equality is already outside the retry policy.

The exact edge matters

As a derived boundary example, suppose attempt 2 finishes at 09:59:54Z on October 2 with Retry-After: 6. The required 6-second wait ends at 10:00:00Z, exactly the cutoff. Do not send attempt 3. A finish one second later would pass the cutoff and also stop. A finish one second earlier would place the next start at 09:59:59Z, inside the time gate, but the other retry conditions must still hold.

Expiry does not establish failure. The server may discard its key cache after retention. Even retrying the old key could then create a duplicate durable effect. Pause dispatch and resolve the original intention before any explicit new one.

The cutoff limits when the client sends more requests. It cannot undo a reservation already committed or make an uncertain record suddenly certain.

06 / Another delivery channel

A callback can repeat a fact you already know

Source rules R06, R11, R13

A callback is a later message sent to the receiver about a reservation. It may arrive after an HTTP response, instead of a response the client saw, or more than once. Delivery can duplicate even when creation happened only once.

eventId
Identifies the event. A redelivery repeats this same identifier.
reservationId
Identifies the durable booking whose state is being described.
intentionId
Connects the event to the original booking intention.
revision
An integer used to order state for this reservation. It is not a global clock.

Trust first, interpret second, acknowledge after saving

  1. 1

    Check authenticity and binding

    The callback must pass the contract’s signature check and intention-to-reservation binding check before entering the event flow. Plausible IDs and neatly formatted JSON are not authentication. A different intention must not replace the original record.

  2. 2

    Check event identity and reservation revision

    Recognize processed event IDs, compare the revision for this reservation, and reconcile conflicts or missing history when required. The next section works through those decisions.

  3. 3

    Save the receiver’s decision durably

    Record processed event IDs and reservation revisions in the receiver’s ledger. The event’s effect must survive a restart.

  4. 4

    Acknowledge only after the ledger update succeeds

    If saving fails, do not report successful processing. The sender may deliver the event again, and the receiver must remain able to handle that repeat.

This sequence describes prerequisites for successful processing. A failed authenticity check does not advance into event interpretation; unresolved evidence requires reconciliation rather than an invented state transition.

This is a contract explanation, not an authentication implementation. The material supplies no actual secret or signature algorithm. The formatted example records below do not establish that any real callback passed authentication.

07 / State over time

A later delivery can contain an older fact

Source rules R11–R13

Deduplicating event IDs solves one problem: the same event arriving twice. It does not solve a different event identifier carrying older reservation state. For that, compare revisions within the same reservation.

The four supplied deliveries all concern reservation res_lantern_C07_C08_7001 and Mina’s original intention. To follow the state changes below, assume each delivery first passes the required authenticity and binding checks and the necessary ledger updates succeed.

The edge cases around a revision

Lower revision
It cannot overwrite newer stored state for that reservation, even if it arrived later or uses a previously unseen event ID.
Same revision, conflicting state
This is an inconsistency. Reconcile it; do not let the last arrival win.
A gap in revisions
Events may be missing. Obtain current authoritative status before applying a transition that depends on the missing history. A larger number alone does not supply that history.
A timestamp
A timestamp alone cannot safely order the local outcome. Use the contract’s revision rules and reconcile where they require it.
A different reservation
Revision numbers across separate reservations are not globally comparable. Revision 8 on one reservation does not order an event at revision 2 on another.
Check your reasoning: why isn’t delivery 4 a harmless duplicate that the event-ID check will catch?

Its event ID, evt_created_late_copy_7003, differs from the first event’s ID. The event-ID check alone cannot classify it as that same redelivery. The revision check shows its state is stale: revision 1 cannot replace stored revision 2.

08 / When sending stops

Exhausting the budget does not settle the booking

Source rules R14–R15

If attempt 4 ends with an unknown result, the intention remains UNKNOWN. The app must not relabel it FAILED simply because it has no retries left. “No more automatic requests” describes the client’s policy; it does not describe the server’s reservation record.

Reconciliation means checking the authoritative record

  1. 1

    Keep the original identity

    Preserve the intention, exact body, key, timestamps, attempt count, and received evidence. Do not generate a fresh key as a way out of uncertainty.

  2. 2

    Read authoritative status

    Use the contract’s read-only status reconciliation with the original intention and key. This asks what happened; it does not dispatch another booking.

  3. 3

    If the answer is still unknown, involve a person

    Keep the unresolved state and investigate. Do not claim a reservation definitely exists, release a local promise of seats as though failure were proven, or start an explicit new intention before resolving the old one.

The hypothetical contract supplies an authoritative status mechanism but no real endpoint. This guide does not invent a URL, polling schedule, guaranteed response time, or working service for it.

Example reader-facing status: “We could not confirm whether your seats were reserved. Automatic attempts have stopped. We are checking the original request before starting another booking.”

This is illustrative wording. It keeps the uncertainty visible and does not claim confirmation or failure.

Closing the waiting screen does not cancel the reservation

Local cancellation

The user cancels the waiting screen. The client stops its local retries.

The server’s possible reservation is still unresolved.

Confirmed server-side cancellation

A distinct server operation confirms the reservation is cancelled.

That operation is outside this retry policy.

The cancellation in the callback log is a reported reservation fact. It is not evidence that closing a screen performs that operation. Likewise, waiting for a key to expire does not cancel anything.

Check your reasoning: the fourth attempt timed out and the user closed the screen. Can the app mark the reservation failed?

No. Both events stop further local activity, but neither proves the server failed to reserve the seats. Preserve UNKNOWN, reconcile using the original intention and key, and involve a person if the result remains unknown.

09 / The useful guarantee

The protection is precise—and limited

Source rule R16, supported by R03–R04

One accepted key, within retention, protects one exact body from duplicate reservation creation.

Each part matters. “One key” limits the identity covered. “Exact body” limits the request covered. “Within retention” limits the duration. And protecting against duplicates still does not promise that a reservation will succeed.

No global exactly-once delivery
Responses and callbacks can repeat. One reservation can generate several deliveries of evidence.
No universal protection across fresh keys
New keys do not share this one-key guarantee. An unresolved intention is not permission to create another identity.
No guarantee of available seats
Duplicate-creation protection does not promise that C07 and C08 can be allocated.
No deadline for human resolution
The retry schedule is bounded; how quickly a person can settle an unknown outcome is not bounded by these rules.

Use three questions to keep the reasoning straight

  1. Which identity does this evidence belong to?Match the intention, exact request, key, reservation, and—where relevant—event ID.
  2. What does it actually establish?Distinguish committed state, acknowledged processing, attempt-specific rejection, and an unknown effect.
  3. What action is still allowed?Apply the response rule, persisted attempt budget, conservative time cutoff, and revision or reconciliation requirements together.

The safest useful result can be an honest unresolved status with the original records preserved. Good retry handling tracks identity and evidence as carefully as it counts seconds.
