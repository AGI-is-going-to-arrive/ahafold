读请求流程 看保证边界

JSON 解析成功，
不代表它是 User。

这段 loadUser 会发出请求、检查 HTTP status、解析 JSON。末尾的 as User 告诉 TypeScript 如何看待结果，不会检查服务器返回的字段。

先看这 6 行

可直接选中代码复制；窄屏可在代码区横向滚动。

snippet.ts · 原代码

type User = { id: string; name: string };
async function loadUser(id: string): Promise<User> {
  const response = await fetch(`/api/users/${encodeURIComponent(id)}`);
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return (await response.json()) as User;
}

async 让函数返回一个 Promise。await 暂停当前函数后续步骤，等待结果，不会阻塞整个页面。Promise<User> 描述成功结果的静态类型，并不承诺请求一定成功。

运行时，按这三步继续

前一步成功，才走下一步。response 是 HTTP 响应对象；真正的数据要等读取响应体后才拿到。

请求前：拼接 URL。encodeURIComponent(id) 把 id 编码为 URL 中的一个组成部分。

例如 id = "a/b"→请求路径 /api/users/a%2Fb

编码让 / 等字符以转义形式进入 URL；它不验证用户是否存在，也不检查访问权限。

  1. 1

    fetch：取得 Response

    const response = await fetch(…)

    未指定 method，默认发出 GET 请求。拿到状态和响应头后，可以得到 Response；此时响应体不一定已读完。

    继续条件：fetch 成功返回响应。404、500 也可以进入下一步。

    失败出口：请求层出错

    例如网络故障或浏览器 CORS 拦截，使 fetch 的 Promise 被拒绝；await 抛出错误。

    此时不会执行 HTTP status 检查。

  2. 2

    response.ok：检查 HTTP status

    if (!response.ok) throw new Error(…)

    ok 在 status 为 200–299 时是 true。这行代码检查状态码，尚未解析 JSON。

    继续条件：response.ok === true。2xx 只通过这一关，不保证响应体正确。

    失败出口：状态不通过

    ok === false 时主动 throw。例如 404 会产生消息为 HTTP 404 的 Error。

    不会调用 response.json()，也不会读取错误响应体中的详情。

  3. 3

    response.json()：读取并解析 JSON

    await response.json()

    异步读取响应体，并把 JSON 解析为 JavaScript 值。合法 JSON 也可以是数组、数字或 null，不一定是用户对象。

    继续条件：读取与解析成功。函数随后返回这个值。

    失败出口：响应体出错

    读取失败会报错；内容不是合法 JSON 时，解析通常抛出 SyntaxError。

    例如 204 虽通过状态检查，但空响应体不能被解析为 JSON。

所有失败都向调用方传递。函数没有 catch：未处理的错误会让 loadUser 返回的 Promise 进入 rejected（失败）状态。调用方可用 try/catch 包住 await loadUser(id)。

as User 没有增加一道验证

它是编译时的类型断言：“把这个表达式当作 User。”类型断言在编译后的 JavaScript 中会被移除，不会检查、补齐或转换字段。

运行时：实际收到的值

{"id": 42}

假设 status 为 200，这份 JSON 可以正常解析。id 仍是数字，缺失的 name 读取为 undefined。

编译时：TypeScript 眼中的类型

{ id: string;
name: string }

经 as User 后，调用方会获得 User 的类型提示。对这个结果访问 name.toUpperCase() 可通过类型检查，却会在运行时报错。

type User 与参数上的 id: string 同样属于静态类型信息。它们帮助 TypeScript 检查代码，不会自动验证外部数据。

以下是按代码推演的教学示例，未发送真实请求。成功对应 Promise 的 fulfilled 状态，失败对应 rejected 状态。
请求 / 响应停在哪里loadUser 的结果
网络故障，未取得响应第 1 步 · fetch失败，向调用方传递请求错误。
404 + 任意响应体第 2 步 · HTTP status失败，抛出 Error("HTTP 404")；不解析响应体。
200 + not JSON第 3 步 · JSON parsing失败，JSON 语法无效。
204 + 空响应体第 3 步 · JSON parsing失败，虽然 ok 为 true，空内容仍无法解析。
200 + {"id":42}走完，返回值成功返回 { id: 42 }，即使它不符合 User。
200 + {"id":"u1","name":"Lin"}走完，返回值成功返回该对象；这次数据恰好符合 User，代码没有做字段验证。

这段代码的保证，到哪里为止？

正常返回，可以推断

  • fetch 返回了响应，且 response.ok 为 true，也就是 status 在 200–299。
  • 响应体成功读完并解析成了一个 JavaScript 值；返回的是这个值。
  • TypeScript 调用方把成功结果视为 User，获得相应类型检查与提示。

仍然不能保证

  • 值是对象、含有 id 和 name，或这两个字段都是 string。
  • 返回的 id 对应请求的用户，或数据内容在业务上正确。
  • 请求一定成功或在指定时限内完成。代码没有配置超时、重试，也没有把错误恢复为默认用户。

若需要可信的 User，应在 JSON 解析后、返回前增加运行时字段校验：确认值是非空对象，且 id、name 都是字符串；必要时再检查 id 是否匹配请求。这些是原代码尚未实现的检查。
