把复杂，展开讲。

loadUser 会发出请求，
但不会证明你拿到了 User。

fetch、response.ok、response.json() 和 as User 排成一条看起来会返回 User 的流水线。前三步在运行时各看一件事；最后一步只在编译期改类型标签，读不到 JSON 字段，也不会因为形状不对而抛错。

原代码

单击下面这块代码可选中全文，再复制。

type User = { id: string; name: string };
async function loadUser(id: string): Promise<User> {
  const response = await fetch(`/api/users/${encodeURIComponent(id)}`);
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return (await response.json()) as User;
}

函数签名写成 Promise<User>，调用方会把结果当 User 用。下面按执行顺序拆开：每一步真正检查了什么，以及什么会原样通过。

四层不是同一种检查

  1. 1 fetch

    发出 HTTP 请求，等待 Response。

    不把 404、500 当成失败。URL 里的 id 会先经过 encodeURIComponent。

  2. 2 response.ok

    看 status 是否落在 200–299。

    为 false 时抛出 Error(`HTTP ${response.status}`)，不读 body。

  3. 3 response.json()

    按 JSON 语法解析 body。

    得到任意 JSON 值：对象、数组、null、数字、字符串都可以。不看 User 字段。

  4. 4 as User

    告诉 TypeScript：把上一步的值当作 User。

    编译后这条断言消失。运行时既不读 id / name，也不抛错。

每一层看见的，和看不见的

把 loadUser("ada") 想成过四道关。关卡名称都是代码里的 API；它们的检查范围并不重叠。

代码 会检查 不会检查 失败时
fetch(...) 请求能否发出并得到 Response HTTP status、body、字段类型 Promise 拒绝（网络错误、被中止、常见 CORS 失败）
response.ok status 是否为 200–299 body 是不是 JSON，更不是 User throw new Error(`HTTP ${response.status}`)
response.json() body 能否按 JSON 解析 id、name 在不在、是不是 string 解析失败时 Promise 拒绝，常见为 SyntaxError
as User 无。它不读取值 运行时的一切 不失败

encodeURIComponent(id) 属于第 1 层的准备工作：把 id 编进路径片段，避免 /、? 这类字符把 URL 拆开。它不验证 id 在业务上是否合法，也不影响后面三层。

同一次调用，失败停在不同层

选一种情况。状态文字会写「继续」「抛错」「未执行」或「不检查」；颜色只是辅助，不单独承担含义。

  1. fetch 继续 抛错 未执行
  2. response.ok 继续 抛错 未执行
  3. response.json() 继续 抛错 未执行
  4. as User 不检查 未执行

status 为 2xx，body 是 {"id":"1","name":"Ada"}。四步都走完，返回值碰巧符合 User。as User 依然没有验证字段；它只是没有挡路。

fetch 的 Promise 拒绝。后面三层不会执行。这不是 HTTP status：函数还没有 response，也就谈不上 ok 或 json()。

fetch 已经拿到 Response。response.ok 为 false，抛出带 HTTP 404 的 Error。json() 不会被调用，即使 404 的 body 里是一段 JSON。

ok 为 true，所以 status 这关放过。HTML 不是合法 JSON，response.json() 失败。as User 不会执行。

JSON 语法成立，解析结果是 null。as User 把它标成 User 并返回。调用方写 user.name 时，运行时才会出问题。

body 为 {"id":1,"name":"Ada"}：HTTP 成功，JSON 合法，断言通过。编译期仍认为 user.id 是 string；运行时它是 number 1。

教学约定：这里的「网络失败」包括连不上、请求被中止，以及浏览器里常表现为网络错误的 CORS 失败。本页没有实际发请求。

as User 改的是类型，不是数据

类型断言发生在 TypeScript 编译期。它让 loadUser 的函数体满足 Promise<User> 这个签名，从而调用方可以写 user.name 而不报类型错误。

常见 DOM 类型里，response.json() 的返回类型是 Promise<any>。any 可以赋给 User，所以去掉 as User 之后，编译也常常仍然通过。断言在这里主要是显式标记；若项目把 json() 标成 Promise<unknown>，断言才成为通过编译的手段。两种情况下，运行时都不会多出任何检查。

你写的 TypeScript

return (await response.json()) as User;

编译后大致剩下的运行时

return await response.json();

右侧是示意，不是本页实际跑过的编译器输出。要点是：as User 在发出的 JavaScript 里通常不存在，因此它不能在浏览器里拦住错误形状的 JSON。

这段代码能够、不能够保证什么

下面的「能够」都带条件：实现需符合常见 Fetch 行为，且调用发生在能处理相对 URL /api/users/... 的环境（浏览器页面里通常可以；没有 base URL 的 Node 需要另配）。

能够

  • 把 id 做 encodeURIComponent 后再放进路径。
  • 在拿不到 Response 时失败（由 fetch 拒绝），而不是返回一个假的 User。
  • 在 status 落在 200–299 之外时抛错，并且不解析错误页 body。
  • 在 body 不是合法 JSON 时失败，而不是把 HTML 字符串当成 User 返回。
  • 让 TypeScript 调用方把返回值当成 User：这是编译期约定，不是运行时证明。

不能够

  • 不能证明 JSON 里真有 id 和 name，也不能证明它们是 string。
  • 不能区分「用户存在」和「服务器用 200 回了一段别的 JSON」。404 会被第 2 层拦住；200 加错误形状会被放行。
  • 不能把 fetch 成功理解成业务成功。fetch 在 404 时仍然 resolve。
  • 不能在 204 No Content 这类 ok === true 但 body 为空的响应上成功：第 2 层会放过，第 3 层通常会在 json() 失败。
  • 不能在运行时维持 Promise<User>。签名在编译后不再约束数据。

loadUser 保证的是请求过程按这四步走完，不是保证结果是 User。若需要运行时形状，要另做校验（例如逐字段检查，或使用独立的 schema 库）；那已经超出这段代码。

这张流水线类比停在哪里

把四层画成关卡，只为了分开「网络 / status / JSON 语法 / 类型标签」。真实 HTTP 还有重定向、编码、流式 body、拦截器，本页不覆盖。

response.ok 按常用 Fetch 行为对应 status 200–299（含 200 与 299）。本页未联网核对规范原文，把它标为教学说明。若运行时的 fetch 不是这份行为，第 1、2 层的边界会不同。

为什么 404 不在 fetch 里抛错？

常用 Fetch 把「拿到了 HTTP 响应」和「业务成功」分开。404、500 仍然是合法响应，所以 await fetch(...) 会得到 Response。这段代码用 if (!response.ok) 把非 2xx 转成抛错；没有这行，json() 就会去解析错误页。
