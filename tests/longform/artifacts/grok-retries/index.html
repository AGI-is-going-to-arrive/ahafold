把复杂，展开讲。

请求没回完，
座位算订上了吗？

灯笼订票台（Lantern）是一份教学用的虚构社区演出订座系统。真正难的不是“再点一次”，而是：网络请求没有干净结束时，客户端到底知道什么。

超时或断线只说明结果未知，不证明订座失败，也不证明座位还空着。一次订座意图可以活过多次网络尝试；一次成功回应，也可能只是在描述这次尝试到达之前就已经存在的预订。数请求、数成功回应、数回调，都不是可靠的预订计数方法。自动策略一共只发四次，并在本地钥匙创建满 24 小时后停止自动重试。用尽之后，未知仍是 UNKNOWN，要用原来的身份去做只读核对。

下面的人名、编号、时间和演出记录都是原例子。规则是一份假定的约定，不是对真实支付机构的描述。预订会占座位；这个例子既不收钱，也不连接真实服务。本页不用插画，关系、条件和数字都写在可编辑的文字、表格和图示里。

先分成三件不同的事

如果把“点一次订座”当成一件事，后面的超时、重试和回调都会缠在一起。这份约定把它们拆成三种对象。

订座意图
一个人决定要请求哪些座位。它先存在于人的决定和本地记录里，不等于已经发出去的网络包，也不等于服务器上已经占座的记录。
HTTP 尝试
一次把该意图送到服务器的网络请求。同一次意图可以对应好几次尝试。
耐久预订
服务器上一条已提交的记录，并且会消耗那些座位。成功回应可以描述一条在这次尝试到达之前就已经存在的预订。

因此，计数对象一旦选错，结论就会错。请求次数、成功回应次数、回调次数，在这份约定里都不是预订次数。

发出去之前，先把意图记下

在发送任何请求之前，客户端要在耐久的本地账本里保存四样东西：意图标识、精确的 UTF-8 请求体、幂等钥匙，以及这把钥匙的创建时间。账本属于这套虚构系统的一部分，不是在要求你去实现某种存储或服务。它在这里的目的，是让客户端重启之后仍能保住“用户当时到底要订什么”。

派遣次数也要写进账本：每次真正派出之前先计数，这样重启不会把四次预算清零。

对这张记录，保守的自动重试截止时间是钥匙创建之后 24 小时，也就是 2026-10-02T10:00:00Z。即使服务器实际接受第一次请求的时间更晚，客户端仍按更早的本地创建时间停手。这个 24 小时是安全边界，不是“永远恰好一次”的保证。

同一把钥匙，必须是同一串字节

对同一次意图，每一次重试都使用同一把钥匙，以及完全相同的请求体字节。服务器把钥匙绑到那些字节上，而不是绑到“看起来相似的 JSON”。

座位选择、出席者姓名，或 JSON 属性顺序一旦改变，都需要一次显式的新意图。但更早那次如果还没有对上，必须先和解，不能直接换一单了事。

冲突时不要把它当成可重试的小错误。用同一把钥匙配上不同字节，服务器返回 409 KEY_PAYLOAD_MISMATCH，并且不为这次冲突的尝试创建新预订。客户端应停止并调查，而不是对着这场冲突继续重试。

服务器只记得一段时间

从第一次被接受的请求起，服务器保留钥匙绑定和最终结果 24 小时。同一把钥匙的并发请求会串行化：最多提交一条预订，后来被接受的尝试收到已保存的结果。

仍在处理中的请求可以返回 202 PENDING。这是在承认“我接到了”，不是已经提交预订的证明。保留期结束之后，服务器可能丢掉钥匙缓存；那时再拿一把旧钥匙重试，未必还能挡住一次重复的耐久效果。所以客户端要先暂停派遣，并解决原来的意图，才能开始任何显式的新意图。

缺回应，留下的是知识缺口

服务器可能已经提交了预订，随后在回应到达客户端之前丢失连接。因此，超时或网络断开的含义是：结果未知。

它不能据此成立下面任何一句：预订失败了；座位仍空着；再开一笔全新订座是安全的。

客户端把该意图标为 UNKNOWN，保留原来的身份，并且只能在后面的有界策略内重试。

客户端此刻看见

这次 HTTP 尝试没有干净结束。本地账本里仍是原来的意图、钥匙和字节。

已知：结果未知。

服务器上可能已经发生

可能尚未占座，也可能已经写下耐久预订，只是那张回条没有送到。

未知：效果在哪一边。

503 TEMPORARILY_UNAVAILABLE 也落在这条缺口里：它可能出现在工作开始之前，也可能出现在开始之后，所以效果同样未知。这与 429 不同——在这份约定里，有效的限流发生在预订处理之前，这一次尝试没有造成预订。

效果发生了，不等于你已经收到

耐久效果和投递是两件事。回应是一条通道，回调是另一条。两条都在讲同一个已提交事实时，本地不能记成两笔预订。

回应分别证明什么

201 RESERVED 最终成功。带有预订标识，以及服务器当前的预订修订号。确认本意图已有耐久预订。 不证明全局恰好一次投递；若稍后又收到 reservation.created，也不能再记一笔本地预订。
回放得到的 200 RESERVED 完成过的钥匙再次出现时，可能带回同一个预订标识。 这一次尝试并没有再分配额外座位。

窄屏可横向滚动对照表。下一节把“还要不要再发”的规则一次列清。

明确的否定回应

这些含义属于这份虚构约定，本文不声称每一种真实 API 都使用相同的状态语义。

400 INVALID_REQUEST
对这次提交的请求体是最终结果，并且不造成预订。客户端应停止，并展示校验问题。
429 RATE_LIMITED
在预订处理之前拒绝这一次尝试，并提供一个有效的整数 Retry-After（单位：秒）。这一次没有预订。
503 TEMPORARILY_UNAVAILABLE
可能发生在工作开始前，也可能在开始后，所以效果未知。它与超时、断线走同一条“可按预算重试”的路，而不是 429 那条“这次没占座”的路。

一个很小的重试预算，条件都写明

自动策略只做这些事。

  • 最初一次，加上最多三次重试：一共四次尝试，不是四次重试。
  • 派遣次数在发送前耐久计数，应用重启不会重置预算。
  • 第 2、第 3、第 4 次尝试之前的基数等待分别是 1、2、4 秒。等待从上一轮结束或超时之后开始。
  • 等待本身不消耗一次尝试。
  • 尚未结束的异步处理走核对，而不是立刻再派发一次订座请求。

限流等待取较长的那一个

遇到可重试的 429 之后，下一次等待取“即将到来的那一次尝试的基数等待”和该回应 Retry-After 之中较大的那个。不要把两段等待加起来。

下一次等待 = max（下一次的基数等待，Retry-After）

第 2 次之后，基数等待是 2 秒。若 Retry-After: 6，就等待 6 秒，不是 2 + 6 = 8 秒。

若对方给出 0 秒延迟，也绝不会取消基数等待；此时仍等待 2 秒。

如果这段必需的等待会到达或越过保守的钥匙到期时间，就停止自动重试，改为核对。到期时间按更早的本地钥匙创建时间起算 24 小时。

教学时间表：三次超时，第四次成功

这份教学日程假定：每一次尝试都恰好用 0.5 秒到达回应或超时；时钟稳定；没有抖动。从 t = 0 起，三次可重试超时之后再一次最终成功，尝试开始于 0、1.5、4 和 8.5 秒；最后一次回应在第 9 秒到达。

真实系统还要处理变化的延迟、时钟不确定、取消，以及常常存在的抖动。这些是提醒，不是偷偷加进这份时间表的额外条款。

同一条时间线，不要把限流例子混进去

上面的 0、1.5、4、8.5、9 只适用于“三次可重试超时，然后成功”。Retry-After: 6 是另一条规则的例子：第 2 次之后基数等待是 2 秒，实际等待取 6 秒。若还沿用“每次恰好 0.5 秒”，第 2 次在 2.0 秒结束，第 3 次会在 8.0 秒开始。8.0 不是材料里单独给出的时刻，而是把限流规则接到这条 0.5 秒假设上得到的。

限流后的等待是“取较大值”，不是相加。脚本若在运行，选中的一行会加上浅底；即使脚本不运行，四行规则仍然完整可读。

看到什么，下一步做什么

把一次尝试的观察、这份约定下已知的效果、以及自动策略的下一步放在同一张表里。缺字段或字段畸形时，证据本身不可信，不能当成一次干净的成功或失败。

回调按自己的顺序到达

事件身份不是预订身份。每一次回调都带有 eventId、reservationId、intentionId，以及整数 revision。

  • 重新投递会重复同一个事件标识。
  • 接收方要耐久记录已经处理过的事件 ID，以及预订修订号。
  • 只有这笔账本更新成功之后，才能确认投递。保存失败不得报告成处理成功；发送方仍可能再投一次。
  • 即便预订本身只提交过一次，事件投递仍可能重复。

按修订号，不按到达顺序

对同一条预订：比已保存修订号更低的回调，不能覆盖更新的状态。同一修订号却带着互相冲突的状态，是需要核对的不一致。修订号出现缺口时，可能意味着漏掉了事件：在应用一段依赖缺失历史的转换之前，接收方要先取得当前权威状态。

单靠时间戳不能安全地排列本地结果。不同预订上的修订号也没有全局可比性。

先鉴别，再解释。回调必须通过这份约定的签名检查，以及意图到预订的绑定检查，才能进入上述事件流程。一个看起来像那么回事的标识，或一份整齐的 JSON，并不能建立真实性。本例不提供真实密钥或签名算法，因此也不声称实现了鉴别。点名另一个意图的回应或回调，不得悄悄替换原来的记录。

停止发送，不是证明失败

第四次尝试之后，如果结果仍未知，它继续是 UNKNOWN。不能只为了让界面整齐，就改标成 FAILED。

客户端要用原来的意图和钥匙，做这份约定里的只读状态核对。教学约定提供了一种权威状态机制，但没有真实端点。若状态仍未知，由人来调查。

这时客户端明确不做的事

  • 不生成一把新钥匙。
  • 不把本地“座位已经到手”的承诺当成已获证明而放开。
  • 不告诉用户预订一定存在。

到期是安全边界，取消等待画面也不是取消预订

服务器在保留期结束后可能丢弃钥匙缓存。那时再重试一把旧钥匙，也许再也不能抑制一次重复的耐久效果。因此客户端要暂停派遣，并先解决原来的意图，然后才能开始任何显式的新意图。

用户取消本地等待画面，同样只停止本地重试，并不取消服务器上可能已经存在的预订。一次经确认的服务器端取消是另一项操作，并且落在这份重试策略之外。

预算用尽，结果未知
保持 UNKNOWN，用原意图和原钥匙做只读核对。下一步是证据，不是新的占座请求。
等待将触及 24 小时边界
停止自动重试，改为核对。客户端按更早的本地钥匙创建时间计算这条边界。24 小时保留不是永恒的恰好一次保证。
关掉等待画面
停止本地重试。服务器上的预订可能仍在。真正取消预订需要单独、已确认的服务器操作。
想改座位或姓名
那是新的意图，但必须先和解尚未解决的旧意图。把新字节塞进旧钥匙会得到 409，并且不为冲突尝试创建预订。

窄保证，以及能带走的判断

在所述的服务器约定下，保留期内一把被接受的钥匙，保护那一串精确字节不会被重复创建预订。理解重试，就是像数秒一样仔细地追踪证据和身份。最稳妥且仍然有用的结果，可以是一个诚实的未决状态，并保住原来的记录。

它没有承诺这些事：全局恰好一次投递；换一把新钥匙也不会重复；座位一定还有；人会在多快之内消除不确定性。

  1. 先问计数对象是哪一种。意图、尝试、回应、回调、预订，五种东西可以不是一对一。
  2. 没有干净结束时，先写 UNKNOWN。不要把缺口补成失败，也不要补成成功。
  3. 重试只重复身份，不发明身份。同一把钥匙、同一串字节；派遣次数写在账本里，重启不得清零。
  4. 等待取较长者，零延迟不能删掉基数等待。必需等待会碰到 24 小时边界时，停手去核对。
  5. 回调看事件 ID 和修订号。重复事件不是第二笔预订；更低的修订号不能覆盖更新状态；迟到的 created 不能恢复已经取消的座位。
  6. 停发之后仍有工作。只读核对、保留原记录。本地取消等待不是服务器取消。
用 Mina Patel 这一单，把容易走错的一步标出来

账本已经写下 C07、C08 和姓名 Mina Patel。第一次尝试超时。这时座位可能已经被占，也可能没有。若立刻换一张“看起来更正”的请求——比如把 JSON 字段调换顺序，或改出席者姓名——却仍使用同一把钥匙，得到的是 409 KEY_PAYLOAD_MISMATCH，并且不为这次冲突尝试创建预订。

正确的路是：保留原来的意图，按预算用同一串字节重试或核对。只有旧意图被解决之后，显式的新意图才可以开始。

若第四次仍未知，界面可以继续显示“尚未确定”，而不能显示“订座失败”或“座位已锁定”。教学约定里的权威状态机制此时是只读的；本页没有真实端点可供查询。

假设、来源与能说到哪里

本页只使用所附教学材料中的虚构约定与原例子，没有查阅外部接口文档，也没有连接真实服务。材料声明：所有名称、标识、时间戳和事件记录都是原创例子；规则不是对真实支付机构的主张。

  • 可以支持的结论：在这套写明的钥匙绑定、24 小时保留、四次尝试、等待规则和回调修订号之下，一次不完整的网络往返究竟证明什么、不能证明什么。
  • 不能支持的结论：某个真实票务或支付 API 使用相同状态码含义；现实网络会按 0.5 秒一次、无抖动运行；座位库存、收费或签名算法的具体实现。
  • 教学假设：每次尝试恰好 0.5 秒；时钟稳定；无抖动。真实系统还要处理变化延迟、时钟不确定、取消和抖动——材料把这些标为提醒，而不是时间表里的隐藏条款。
